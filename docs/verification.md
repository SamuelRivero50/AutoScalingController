# Verification Checklist

Every claim in this design falls into one of two categories, and this document is explicit about which is which — an assumption is only left open here if there is genuinely no documentation that can settle it; anything settleable by an authoritative source is verified before this checklist is written, not deferred to it.

## Why these specific items remain open

Each remaining item depends on the state of *this specific AWS Academy Learner Lab account, at the time of the real run* — not on a fact AWS publishes generally. No AWS document can say what a particular student's lab instance will permit at a particular moment; that can only be observed by running against it. This is different from a claim like "does IAM support ARN restriction for this action," which AWS does publish and document — those claims are verified below via the AWS Service Authorization Reference and are not repeated as open items.

- [ ] **Instance warmup duration** — assumed 180s (realistic profile) pending the dedicated 5-second-interval measurement script run against a real launch (`docs/spec/lifecycle-and-failures.md` §3). *Why this can't be resolved by documentation*: warmup time depends on this account's specific AMI, instance placement, and network conditions at launch time — AWS does not publish a fixed value.
- [ ] **AWS Academy Learner Lab: Detailed Monitoring availability** — confirm whether 1-minute EC2 CPU monitoring can be enabled in this specific lab; if not, confirm the datapoint-dedup safeguard behaves correctly against real 5-minute CPU data (`docs/spec/signals.md` §3). *Why this can't be resolved by documentation*: checked the official AWS Academy Learner Lab Educator Guide directly — it states only that a "restricted set of AWS services" applies and points to a portal-internal resource list, without naming CloudWatch Detailed Monitoring specifically. This is a genuine account-configuration question, not a publicly documented restriction.
- [ ] **AWS Academy Learner Lab: regional instance/vCPU cap** — confirm the exact cap (observed as 9 instances / 32 vCPUs) still applies at the time of the real run, since the controller instance plus up to 5 application instances must fit within it (`docs/context/constraints.md` §1). *Why this can't be resolved by documentation*: this is an account-level service quota set per lab session by AWS Academy, not a documented platform-wide constant.
- [ ] **ALB post-session billing behavior** — reconfirm immediately before the real run that an ALB left running between AWS Academy sessions does in fact continue billing (this was verified via research once; re-confirm against the current lab terms before relying on it for the destroy-per-session policy) (`docs/context/constraints.md` §1, ADR-0016). *Why this is re-checked rather than left as fully closed*: it was already verified once via research (see below), but Academy lab terms have changed before, so this is re-confirmed operationally right before the run rather than assumed indefinitely valid.
- [ ] **t3.micro unlimited-mode surplus cost** — confirm the actual surplus charge incurred (if any) after the real run, and record it in the evaluation report as part of the cost accounting (ADR-0014). *Why this can't be resolved by documentation*: the surplus rate is documented (verified below), but whether any surplus is actually incurred depends on this run's actual CPU usage pattern — that is a measurement, not a lookup.
- [ ] **Health-check timeout tuning** — confirm empirically that the chosen ALB health-check timeout/threshold, combined with the 80-90% stress cap, does not produce a false-positive unhealthy verdict during the real run (`docs/spec/lifecycle-and-failures.md` §5). *Why this can't be resolved by documentation*: this depends on this application's actual response latency under this specific stress load, which only exists once the real run happens.

## Verified via authoritative documentation (not left as open items)

- t3 instances default to `unlimited` CPU credit mode, and `standard` mode would throttle CPU under sustained load — AWS documentation (ADR-0014).
- AWS Academy Learner Lab sessions auto-stop EC2 instances after 4 hours but do not auto-stop the ALB, and billing visibility lags — verified via research (ADR-0016).
- ALBs require at least two Availability Zones — AWS documentation (ADR-0015).
- **`SetDesiredCapacity`, `SetInstanceHealth`, and `TerminateInstanceInAutoScalingGroup` support ARN-level `Resource` restriction and the `autoscaling:ResourceTag` condition key** — confirmed via the AWS Service Authorization Reference for Amazon EC2 Auto Scaling (ADR-0010). This item was previously left as an open verification item on the assumption that ARN-level support was unconfirmed; that assumption turned out to be checkable and wrong, so the policy (`infra/iam/controller-policy.json`) now restricts by ARN as the primary control, with the tag condition kept as a second layer.
